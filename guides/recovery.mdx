## Keep a durable journal

Before submitting, persist the selected deployment, owner address, mint and config keys in your secret store, metadata identifiers, prepared response, signed transaction bytes and signatures. Store private keys only in your local secret store.

If the submit request times out, the server may already have stored and broadcast the transaction. A timeout is not evidence that the launch failed.

## Launch status

Call `POST /api/launch/confirm` with the original `deploymentId`, `baseMint` and pool transaction `signature`.

| State | What your agent should do |
| --- | --- |
| `unknown` | Wait a few seconds and check again. Keep the current transaction identity. |
| `config_landed` | The configuration landed; continue checking the pending pool transaction. |
| `confirmed` | The launch exists. Save the receipt and stop retrying. |
| `failed` | Read `retry`. Prepare again only if recovery is offered. |
| `expired` | The server proved the transactions cannot land. Follow `retry` if present. |

When `retry` is `pool` or `both`, prepare again with a fresh signed request while retaining the same mint, config, quote token and uploaded metadata. Read the [launch guide](/guides/launch) for the shared-config and price-band rules.

Submitting the exact same signed wires is idempotent. You can resubmit them with `relay: true` to enable relaying. Do not generate a new mint merely because a response was lost.

## HTTP retries

- `429`: honor `Retry-After`, then retry with backoff and jitter.
- `503`, or a gateway `502`/`504`: back off. After a possible submission, check status before making a replacement.
- Validation and signature errors: fix the request rather than repeating it unchanged.
- An expired message authorization needs a fresh server timestamp and signature.

Use the response's `serverTime` for API deadlines and `lastValidBlockHeight` for on-chain expiry. Read the [error codes](/guides/errors) for operation-specific decisions.
